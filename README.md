# netix-render

NETIX's HTML render engine: one brand-token source, a sandboxed Jinja2 component library, and
validated contracts for reports and transactional email. Consumed in-process by backend services
and exposed as `documents.*` MCP tools by ml-engine.

## What it renders

- **Report documents** (`netix_render.render_report` / `render_email`): the `ReportDocument`
  contract extracted from ml-engine's report engine: discriminated-union sections (banner,
  kpi_grid, check_table, exceptions, trend_pair, ai_insight, actions, data_table, twocol,
  hbar_chart, rings, footer) rendered to a web page or an email-safe inlined variant.
- **Transactional email** (`netix_render.render_email_template`): registered templates
  (`otp_code`, `report_ready`, `entity_event`, `staff_alert`, `report_pack`, `alarm_notice`,
  `feedback_request`, `status_digest`, `offline_daily_report`, `offline_monthly_report`), each with a strict pydantic
  contract, en/ar/fr/es/nl/de chrome strings, RTL support, and a plain-text alternative:

```python
from netix_render import render_email_template

rendered = render_email_template(
    "otp_code",
    {"meta": {"locale": "ar"}, "code": "482913", "expires_minutes": 10},
)
rendered.subject, rendered.html, rendered.text
```

Select the recipient’s language with `meta.locale`; omitting it defaults to English.
`offline_daily_report` and `offline_monthly_report` also take data-service's flat `language` and
`organization_name` keys, which fill `meta.locale` and `meta.org.name` when `meta` does not set them.
The renderer translates template chrome and default subjects. Callers supply localized
body text, field labels, and action labels. Email action and download links reject active
script, data, and local-file URL schemes.

Every render is deterministic: validation happens against the template's contract
(`extra="forbid"`), CSS is inlined via `css-inline`, and the template API produces complete HTML
from caller-supplied data.

The `v0.1.4` tag accepts `en`, `ar` and `es`. The additional locales, link validation and the
`offline_daily_report` template ship in `v0.1.5`; a service pinned to `v0.1.4` needs a pin update
before it can use them.

`v0.1.6` adds Connectivity v2 to the offline emails:

- `offline_daily_report` accepts optional `subject_line`, `all_clear`, `changes`, `incidents` (at most 20),
  `availability_delta`, `snoozed_count`, `maintenance_count` and `offline_items[].link`, so a `v0.1.5` sender still
  validates. The email leads with what changed since yesterday, then incidents (a gateway incident reads
  "14 assets unreachable"), then the offline list with deep links, by building and gateway impact. `all_clear: true`
  sends a short green "Everything is reporting" email. The subject is `meta.subject`, else `subject_line`, else
  "<report name>, <date>".
- `offline_monthly_report` is new: availability per building (at most 100) for a calendar month, with totals,
  an optional availability target, the devices with the most offline time (at most 20) and an attachment note.
  Availability is floored to one decimal so a missed target never reads as met.
- Both follow the connectivity colour rule (`color.connectivity` tokens): online is neutral grey with a hollow
  circle, degraded is amber with a triangle, offline is red with an octagon, and every status also carries its word.

## Design tokens

`netix_render/tokens.json` is the single brand source, derived from
`frontend-template/app/assets/styles/globals.css` (see the `source.hsl` block; the
`netix tokens check` workspace command and `tests/test_tokens.py` guard drift).
`netix_render/DESIGN.md` is the human/agent-facing design skill describing how to use them.

## Development

```bash
uv sync --group dev
uv run pytest                      # golden-file snapshots; UPDATE_SNAPSHOTS=1 to regenerate
uv run ruff check . && uv run mypy
```

Snapshot updates must be reviewed by eye, open the changed file under `tests/snapshots/`
in a browser before committing.

## Adding an email template

1. Contract model in `netix_render/email/schema.py` (extend `TransactionalEmail`).
2. `netix_render/templates/email/<id>.html.j2` (extend `email/base.html.j2`) and `<id>.txt.j2`.
3. Register in `netix_render/email/registry.py` with a description, default subject, and a
   realistic sample.
4. `UPDATE_SNAPSHOTS=1 uv run pytest` and review the new snapshot.

### Multipage reports

A document containing a `headline_details` section renders as a linked executive summary, one page per headline, and supporting evidence and action pages. Each headline contains a finding, impact, uncertainty, investigation steps, owner/action, and up to four source evidence records. Page composition is deterministic; HTML is never generated by the language model.

Web reports include in-document navigation. A4 print styles insert page breaks and numbered footers; table rows are split into bounded groups. Email renders the same detailed content in a continuous layout. Documents without `headline_details` retain the existing continuous presentation.

### Public example data

Report fixtures and snapshots must be authored from scratch with fictional assets, readings, incidents and `example.invalid` links. Renaming a customer or site is insufficient. Keep production reports, screenshots, raw payloads and validation artifacts outside this public repository, including PR descriptions and attachments. The `synthetic_*` fixtures are deliberately fictional and exercise daily, weekly and monthly report components.

Report branding is supplied through `meta.logo_line`. It is escaped and used consistently in HTML, email and every multipage header. Omitting it renders reports without an organization label. Report metadata supplies asset names and timestamps; the renderer does not invent copyright ownership or verification destinations.
